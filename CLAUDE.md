## The UI tools in this project

Three reusable UGUI tools, each a self-contained folder with its own `README.md`. **Read the relevant README before changing a tool.** They are independent — no tool references another.

| Folder | What it does | Namespace |
| --- | --- | --- |
| `DOTweenAnimationPlayer/` | Inspector-authored DOTween animations, played by name | `rmf_claude.DOTweenUI` |
| `FlipbookAnimation/` | Sprite-frame flipbooks on UGUI `Image`s | `rmf_claude.FlipbookAnimation` |
| `SelectableEvents/` | UnityEvents for Selectable pointer/selection callbacks | none — global |

`SelectableEvents` is hand-written by the project author. Do not restructure, namespace or "modernise" it without being asked.

Common to all three: runtime types are `public`, editor-only drawers and custom editors are `internal`, and the `.meta` files carry the script GUIDs — **a folder copied without them loses every component on existing prefabs.**

**Do not add an `.asmdef` to any of these folders.** DOTween's UI shortcuts (`DOAnchorPos`, `DOFade`, `DOColor`, `DOSizeDelta`, the TMP ones) are *generated by the DOTween Setup panel* into `Assets/Plugins`, which compiles into the predefined assembly `Assembly-CSharp-firstpass`. An asmdef cannot reference a predefined assembly, so adding one silently deletes every one of those shortcuts — no error, just methods that no longer exist. The `Editor/` subfolder name is the only mechanism used to separate editor code, and it needs no configuration.

## DOTweenAnimationPlayer

Requires **DOTween Pro**. After importing it, run `Tools → Demigiant → DOTween Utility Panel → Setup DOTween…`; this is not optional and not the same as importing DOTween, and skipping it produces errors pointing at *this* code rather than the real cause.

`UIAnimationPlayer` holds a list of named animations, each a list of steps, and plays them: `player.Play("Show")`. A step drives one property on one target — anchored position, scale, rotation, colour, alpha, size delta, offset min/max, material float/colour, `SetActive`, punch (position, rotation, scale), shake (position, rotation, scale), or a sound. Steps run in sequence or joined to the previous one, with per-step delay, duration, ease and endpoint mode (`Absolute` / `Baseline` / `Current`). It is deliberately generic and knows nothing about menus, HUDs or transitions — **do not add game-specific logic to it.**

Five things are optional and invisible when unused, and an existing player with none of them behaves exactly as it always did: a shared `UIAnimationAsset` in the player's `Shared` slot, a `TargetPath` on a step, the `Play(string, Action<UIAnimationEndReason>)` overload, an animation's own Snapping (one DISABLED / ALL STEPS / PER STEP button in the Inspector, the two bools `Snapping` / `SnapPerStep` in code), and a step's movement path (the `Custom Path` dropdown in the Inspector, `UseCustomPath` + `PathShape` in code, which routes a vector step through waypoints to `To`, with a Scene-view handle editor in `Editor/UIAnimationPathEditor.cs`). The path was added with a before/after fingerprint of every authored animation in `GameCraftSep2026Jam`, which came out byte-identical. Everything else added since is editor-only and cannot change playback: the Scene-view gizmos, the Inspector's type check and its Use Current Value button.

Things that look wrong but are intentional:

- **Reversing is an authoring operation, not a playback mode.** `Mirror Animation` / `Duplicate as Mirrored` rewrite the data once, so a mirrored `Show` is a real, editable `Hide`. There is no runtime `PlayReverse`, and **there should not be** — a live reverse mode and an authored mirror are two answers to the same question, and having both was tried and cut.
- **Mirroring deliberately does not touch easing** — neither the `Ease` preset nor a custom curve. The house style is that things decelerate into place in *both* directions, so a mirrored `Hide` keeps the `Out` ease its `Show` was authored with. Ease inversion was built, then removed on request. Do not reintroduce it.
- **`PlayAnimation` / `StopAnimation` are not redundant wrappers around `Play` / `Stop`.** Unity's UnityEvent dropdown only lists methods returning void with at most one argument, which excludes `Play` (returns a `Sequence`) and `Stop` (an optional parameter reads as two overloads). A void `Play(string)` cannot be an overload — C# does not overload on return type.
- **Stepped playback ("Play At Custom FPS") is implemented on the ease, not on the clock.** It quantises the *time* handed to the underlying ease, so the tween still updates every frame but holds its value between boundaries. Every step shares one grid keyed off its absolute sequence position — per-tween grids read as jitter. Punch and shake are excluded because they drive their own oscillation.
- **`WithPrevious` steps are groups, not rows.** Anything reordering a step list must keep each group's members together and contiguous, or it silently re-parents which steps are joined to which.
- **`AnchoredPosition`, `SizeDelta`, `OffsetMin` and `OffsetMax` all write the same rect.** Unity stores one rect and derives every view from it, so animating two of them on one target makes them overwrite each other. Any new rect-driving step type must also be added to `CaptureBaseline`, or `To: Baseline` collapses the target to zero.
- **A step's `Delay` is applied in exactly one place: the insert position `BuildSequence` computes.** `BuildTween` must never call `SetDelay` — DOTween adds a tween's own delay *on top of* its sequence position, so doing both doubles every delay. This regressed once already.
- `UIAnimationAudio.Shared` is the one global in the folder. For a mixer, call `UIAnimationAudio.SetShared` once rather than adding another.
- **A player deep-clones every animation it takes from a shared `UIAnimationAsset`, and that is correctness, not caching.** `RuntimeSequence`, `RuntimeCallback` and each step's resolved targets (`rect`, `graphic`, …) are ordinary instance fields on `UIAnimation` / `UIAnimationStep`, so two players reading one asset would overwrite each other's live sequences and animate each other's objects. `CloneForRuntime` round-trips through `JsonUtility` and then re-points `OnComplete` at the *original* `UnityEvent` rather than copying it — a persistent-call list is Unity's own serialization detail and a listener list is read-only at runtime. Consequence to keep documented: editing an asset at runtime does not reach players that have already initialised, and assigning `Shared` from code after `Awake` does nothing.
- **`TargetPath` reaches upward as well as down, because `transform.Find` accepts `..`.** Measured in Unity 6000.3: `Find("..")` returns the parent and `Find("../../Name")` walks up twice then down. This is not a curiosity — the common authoring layout puts the player on a child object called `Animations` and drives the *button above it*, which is not a descendant and would otherwise be unshareable. `..` is what makes that layout portable, so do not "fix" `ResolveHost` by restricting it to descendants. Segments resolve one at a time, so `../Self` means "a child of my parent with that name", not "me".
- **A `TargetPath` that matches nothing resolves the target to null, not to the owner.** A step that visibly does nothing is far easier to diagnose than a mistyped `Panel/Icon` quietly scaling the whole panel. `ResolveHost` warns once from `Resolve`, and sets `targetPathMissed` so `HasTarget` does not warn a *second* time on every `Play` — the same precedent the shader-property check already set.
- **The end-callback fire-once flag is a local captured by each play's closure, never a field on the animation.** An `onEnd` that plays the same animation again re-arms the animation while the old play is still tearing down; a guard living on the animation would then let the old play's teardown fire the new play's callback. For the same reason `Kill` only clears `RuntimeSequence` / `RuntimeEndCallback` when they still `ReferenceEquals` the ones it started with.
- **A kill the player did not issue is caught by the sequence's own `OnKill`, and the player deliberately has no `Update`.** `PendingEndReason` carries the reason into that callback: armed as `Stopped`, overwritten by `Kill` before it kills. Every end path therefore has two routes to the same callback — the synchronous invoke in `Kill` and DOTween's own — and the fire-once flag makes whichever arrives second a no-op. A polling `Update` was written first, on a measurement that turned out to be an edit-mode artifact; see the DOTween table below before reaching for one again.
- **Destroying an *enabled* player reports `Disabled`, not `Destroyed`.** Unity runs `OnDisable` before `OnDestroy` and offers no way to know a destroy is coming. That is reported honestly rather than guessed at with heuristics like `scene.isLoaded`; `Destroyed` is what you get when `KillOnDisable` is off or the object was already inactive.
- **`UIAnimationEndReason.NotFound` is deliberately a reason rather than a silent no-callback.** A mistyped animation name is a production runtime failure, and the whole point of that overload is that a caller is never left waiting.
- **The edit-mode preview lifecycle lives in `Editor/UIAnimationPreview.cs`, not in an inspector.** Two inspectors drive it — a player's, and an asset's by way of a player — and a second copy is exactly the kind of thing that ends up with only two of the three load-bearing safety mechanisms. The button rows (`DrawRow` / `DrawFooter`) live there too, for the same reason.
- **Within one player the preview chains; it does not restore between Plays.** `CloseCredits` after `OpenCredits` has to start from the open state or it cannot be judged at all — restoring first made it start from rest, where a close with delayed From steps visibly misbehaves. **A different animation pressed while one is still running finishes the running one first** (`Complete(true)`, which works out of play mode and fires the SetActive callbacks on the way; an endless loop is left where it stands), so where the second starts never depends on when it was clicked — stopping it where it stood was reported as a bug. That is deliberately *not* play mode's behaviour, where `InterruptOthers` stops the running one where it stands; the README says so. **`Reset` re-captures the start snapshot after applying the From values** (`EditorMarkPreviewStart`), so `Play` straight after `Reset` runs from the frame `Reset` showed — without it, Play restored the pre-Reset state (rest) and a close with delayed From steps played from the wrong place. **And every preview `Play` does the same thing first** — `ApplyFromState` then `EditorMarkPreviewStart` — so Play always equals Reset-then-Play. That is deliberately *not* play mode: an animation with `ApplyFromValuesImmediately` off holds each delayed From step at its current value until the step starts, and `CloseCredits` (which has it off) played from rest in the preview showed its buttons at rest, its text with no background, then everything snapping — reported as a bug, since in the game it only ever plays after `OpenCredits`. Proven on the UI prefab: Play from rest and Reset-then-Play give identical samples on all 30 animations. Two things keep chaining safe. (1) *Baselines are still captured at rest before every Play*: `EditorContinuePreview` notes the current state (a per-step **snapshot**, captured and restored through `CaptureBaseline` / `RestoreBaseline` themselves by swapping the snapshot into the baseline fields, so no step type can be covered by one and missed by the other), restores rest, re-initialises there — which also picks up Inspector edits — and puts the noted state back. The notes live on the *previous* runtime list's steps, which still point at what they resolved against. (2) *Play on the same animation again restores that play's start snapshot first*, so iterating on one animation still replays it from the top. A snapshot is only written back if the step still resolves to the same object, so retargeting mid-preview never writes one object's value onto another.
- **`RestoreBaseline` switches on the Type the baseline was captured under (`baselineType`), not the current `Type`.** Changing a step's Type mid-preview otherwise wrote a captured scale into a position. `RestoreBaseline` is editor-only in practice; nothing at runtime calls it.
- **Punch and shake capture a baseline even though nothing at runtime reads it.** It is what lets the preview put back a punch stopped half way through an oscillation — "it returns to its own start value" is only true when it runs to the end. Every impulse type is in `CaptureBaseline` / `RestoreBaseline` under the property it drives (position, `localEulerAngles`, `localScale`).
- **`ShakeRotation` and `ShakeScale` take a per-axis strength (`ToVector`); `ShakeAnchoredPosition` takes one number (`ToFloat`).** Not an inconsistency to tidy: DOTween's single-number rotation shake turns all three axes, and on a flat UI element X/Y rotation reads as it tipping over in 3D, so Z-only has to be expressible. `ShakeAnchoredPosition` predates this and its stored field cannot move.
- **Snapping is resolved as `step.Snapping || (animation.Snapping && !animation.SnapPerStep)`** — `UIAnimation.SnapsEveryStep` is passed into `BuildTween` as `snapAll`. The animation-wide box *adds to* a step's own box rather than replacing it, which is what makes this back-compatible with no migration: older data has the new fields false and snaps exactly the steps it always did. For the same reason the drawer shows a step's own box whenever it is ticked, even with Snap Per Step off — a setting that changes playback must never be invisible. Do not "simplify" this into Snap Per Step choosing between the two; that needs a migration flag and would silently change old data in builds, where `OnValidate` never runs.
- **The Type and Ease dropdowns are `GenericMenu`s drawn by the step drawer, not Unity's enum popup.** Type is grouped into sections derived from `IsImpulse` / `TargetKindOf` and sorted alphabetically *in the drawer*, so the enum's numbers — the serialized contract — never move to make the menu read well. `Custom Curve` is the first Ease entry, but the data is unchanged: it sets the same `UseCustomCurve` bool the old checkbox did, and the Ease row binds `BeginProperty` to whichever of the two fields it is showing so prefab-override bold and Revert follow what is visible. Menu callbacks write through `.Copy()`'d properties and `ApplyModifiedProperties`, because they run after the repaint that drew them.
- **The drawer reads enums with `intValue`, not `enumValueIndex`.** The index is a position in the declaration, only the number is the contract; they agree today only because every enum here is declared in value order.
- **The mode dropdown's tooltip comes from an empty `GUI.Label` drawn over the popup.** A popup does not show its label's tooltip, and the tooltip used to sit on the row's `To` label, where it read as explaining the row rather than the options. A label takes no clicks, so the popup under it still opens. The text is built per dropdown (`ModeTooltip`) from the options that dropdown actually offers — one shared tooltip described `Current` on a dropdown that did not offer it, and was reported.
- **The From dropdown does not offer `Current`, but still shows it when the data has it.** `FromMode = Current` never meant an offset: `HasAuthoredStart` excludes it, so the step ignores its From value and starts wherever it is — the same as the button reading TO. It is kept visible and never rewritten (all 14 `FromMode: 2` in the jam project have `UseFrom: 0`, so nothing authored relies on it), because changing what stored data means is the back-compat line. Contrast the To row with From on, which has always rewritten a stored `Current` to `Baseline` on draw — left alone, flagged here.
- **The Snapping row is one button over two bools** (`UIAnimationSnapModeAttribute` on `Snapping`, `[HideInInspector]` on `SnapPerStep`). Every combination maps to a state — `SnapPerStep` wins, as at runtime — so nothing is rewritten until it is clicked. **The Custom Path row is one dropdown over `UseCustomPath` + `PathShape`** the same way; `Disabled` leaves the shape and points alone. Both bind `BeginProperty` to whichever field decides what is shown, like the Ease row. The same idea, smaller: **Start** is an AFTER PREVIOUS / WITH PREVIOUS button over the unchanged enum (anything but `AfterPrevious` reads WITH, as playback treats it), and **Play At Custom FPS** draws `FPS` inline beside its tick (`UIAnimationInlineValueAttribute`, `[HideInInspector]` on `FPS`), with a `BeginProperty` rect that stops where the field starts so each half keeps its own override bold and Revert. `UIAnimationShowIfAttribute` is unused since; it is left in place as a public type.
- **The step list's row shading comes from ReorderableList's source, not a guess**: `BandLeft = 28` (the list's drag handle 20 + foldout margin 8), `BandRight = 6` (its padding), and vertically the rect handed to the drawer *is* the whole row — the list gives it the element height (property height + `elementPadding` 2) and only moves it down by half the padding (`Defaults.DrawElement`: `rect.y += ElementPadding(rect.height) / 2`). So the band is `y - 1`, exactly `position.height` tall. An earlier guess of 2 above and 4 below ran visibly into the next row; measured after the fix, collapsed rows alternate 28 / 27 px shaded / plain at 125 % scaling, the 27.5 px pitch. `ReorderableList.Defaults` reports `dragHandleWidth 20, padding 6, propertyDrawerPadding 8, elementPadding 2` by reflection if they ever need rechecking.
- **A step the type check finds dead is greyed out below its target** (`DisabledScope`), with its header text faded (`DimFoldout`). The fields that fix it are drawn *outside* the scope — Type, Start, slot and Target Path above it, `Clip` / `ShaderProperty` before it starts — because `DisabledScope`s nest by AND-ing and nothing inside one can be switched back on. A sound whose Target Path misses is warned about but not greyed: it still plays, on the shared source. The warning row itself **wraps** onto as many lines as its text needs (it used to be one truncated line with the rest in a tooltip, which was reported) — see the `GetPropertyHeight` width entry under shared conventions for how its height is measured.
- **Two IMGUI drops, found by screenshot:** `EditorGUI.Foldout` does not draw a `GUIContent` image with the foldout style, and a label drops its image once its text overflows. The header's warning icon and the warning row's icon are therefore separate `GUI.Label`s.
- **Nothing in the Inspector may read `UIMaterialInstance.Material`.** Its first read creates a material instance and assigns it to the Graphic — a side effect in the scene. The type check and Use Current read the source material through `UIAnimationTargets.SourceMaterialOf` (TMP's `fontSharedMaterial`, else `graphic.material`). The edit-mode preview itself still goes through `.Material` on material steps; that predates this and is untouched.
- **Editor-side target resolution lives in `Editor/UIAnimationTargets.cs`, and it mirrors `Resolve` without its side effects** (no warnings, nothing written to the step). A shared asset's steps resolve against the asset inspector's Preview On player, registered in a static map in `UIAnimationAssetEditor` (`PreviewPlayerFor`) because the drawer only knows the serialized object it draws.
- **`UIAnimationSimulation` plays position, size, scale and rotation steps forward on paper**, for the gizmos, the path editor's start point and Use Current's `Current` offset. It must follow playback, and does so by *sharing* code rather than copying it wherever it can: steps are laid out by `UIAnimationPlayer.LayOutSteps` (extracted from `BuildSequence` for this — play-path fingerprint byte-identical), stepped eases go through a real `UIAnimationSteppedEase`, and paths through `UIAnimationPathEditor.Evaluate`. The rules it copies: From state applied first in step order (the preview's rule); steps act in `(start time, index)` order so a later-starting step overrides and among equal starts the lower row wins; a step's start is read at its start time; paths are followed at constant speed (DOTween's `ConvertToConstantPathPerc`); snapping rounds. Checked against the real preview at every drawn moment: 485 moments across the UI prefab and both tester scenes, all within 0.07 units — the residue is DOTween's own path length table. It works from **rest**, which during a preview is what `UIAnimationPreview` captured before anything moved (`NoteRest` / `ForgetRest`), so drawings stay put while the preview moves the objects.
- **Gizmos draw from `UIAnimationPlayerEditor.OnSceneGUI`, which Unity only calls for editors the Inspector has built.** "Expanded" in the gizmo modes is `isExpanded` on *that editor's* `serializedObject`. **But `OnSceneGUI` must not touch `serializedObject` or `targets`**: Unity logs an error with a stack trace on every call, which is every Scene view repaint — it flooded the Console and made the Editor feel sluggish. The editor keeps a reference (`sceneSerialized`) taken in `OnEnable` and refreshed in `OnInspectorGUI`, null when multi-editing. Rainbow colours apply in `Expanded Steps` only (`EffectiveColors`); everywhere else it is Distinct, with the stored choice kept. The simulation behind the gizmos costs about 1.3 ms for all 30 animations in the UI prefab. Two consequences found the hard way: a harness that changes the selection while the Editor is in the background must `ActiveEditorTracker.sharedTracker.ForceRebuild()` or nothing draws, and `isExpanded` set through a *different* `SerializedObject` does not reach an editor that already exists.
- **Use Current's `Baseline` and `Current` only work inside a preview, on purpose.** Out of a preview the object's current value *is* its rest, so both would always store 0. Inside one, rest is the preview's capture and Stop and Restore puts the posed object back — the Animation window's record workflow. **That workflow needs the preview to survive selecting the object being posed**, and it did not at first: the player inspector's `OnDisable` ended the preview on any selection change, so selecting the ball to drag it restored it, and back on the player Baseline and Current were greyed out — reported as "clicking record does nothing", and missed by a scripted test that never changed the selection. `EndIfOwnedBy` now leaves the preview running, owned by nobody, while the selection is on the player, its shared asset or any object it animates, and `Selection.selectionChanged` ends an unowned one once the selection leaves. An owner that still exists (a locked inspector, or a plain `object` from a harness) is left to end its own preview. The asset inspector remembers its Preview On per asset in the static map for the same reason. Rotation reads are wrapped to the nearest angle to zero (`Mathf.DeltaAngle`): a Rotation step is `FastBeyond360`, so a copied `350` would spin the long way.
- **The preview unwinds itself from `[InitializeOnLoad]` hooks** — `playModeStateChanged` at `ExitingEditMode` (which runs *before* Unity backs the scene up for play mode, so the restore is what play mode starts from and returns to) and `beforeAssemblyReload` — not only from an inspector's `OnDisable`. The inspector hook (`OnDisable`) and `Selection.selectionChanged` cover selection change — see Use Current for why it waits for the selection to leave.
- **`EditorSuppressSound` is on for the whole preview, not just while the sequence is built.** Sounds fire from sequence *callbacks* during playback; scoping it to construction silenced nothing, and every preview of a sound step called `UIAnimationAudio.Shared` in edit mode — where `DontDestroyOnLoad` **throws after the GameObject already exists and before the static is assigned**, leaking one `UI Animation Audio` into the open scene per call, outside the Undo record. `Shared` now returns null out of play mode as a second guard.
- **A filled target slot skips the Target Path entirely — the path is not even looked up.** It used to be resolved anyway, and a path that missed set `targetPathMissed`, which then made `HasTarget` skip a step that had a perfectly good direct reference. The drawer greys the path out while the slot is filled so the precedence is visible.
- **An asset inspector's "Preview On" player is not a serialized field on the asset.** A scene reference is the one thing an asset cannot keep, which is the problem the slot exists to work around. It lives in the editor, remembered per asset in a static map until the next domain reload, so a new inspector on the same asset finds it set.
- **Movement paths (`UseCustomPath` / `PathShape` / `Waypoints`) are built on DOTween's generic `PathPlugin`, not a shortcut** — `DOTween.To(PathPlugin.Get(), getter, setter, new Path(...), duration)`, the same call DOTween's Rigidbody module makes. That is what lets one path drive `anchoredPosition`, `sizeDelta` or `localScale`. Three plugin behaviours it works around, measured on DOTween 1.3.030: it **throws a NullReferenceException at startup without `SetTarget(transform)`**; it **ignores `From()`**, so an authored From is supplied by making the getter return it; and it **prepends the start as a point unless the first waypoint already equals it**. `Rotation` is excluded on purpose (quaternion, not Euler), and an empty point list falls back to the ordinary tween so it behaves exactly like the box unticked.
- **Waypoints follow `To`'s mode rather than having their own.** `SetRelative` offsets every path point by the start, To included, so a separate mode would be a second answer to a question To already answers. The cost is in mirroring: when the mirror changes To's mode (From/To in different modes, or no-From with an Absolute To), the points can't be converted without the runtime baseline, so `UIAnimationMirror.PathSpaceChanges` reports them instead of guessing.
- **`UIAnimationPathEditor.Evaluate` reimplements DOTween's Catmull-Rom because the real `Path.GetPoint` is `internal`, and its end conventions are deliberately not the textbook ones:** the control point before the first point is the *second* point, and the one after the last is the last point mirrored through the one before it. Checked by sampling a real path tween — every position lies within 0.001 units of the drawn curve. "Fixing" it to reflected ends draws a curve the object does not follow. The same asymmetry is why a mirrored *Curved* path retraces its original only to within about 1.5 units on a 200-unit path, while *Linear* is exact.
- **The path is created with a transparent gizmo colour.** DOTween draws running path tweens in the Scene view at the raw point values, which for `anchoredPosition` are not world positions.
- **The Scene-view path editor follows Unity's Edit Collider pattern:** it hides `Tools` (restoring the previous value, and again from `beforeAssemblyReload`, because `Tools.hidden` survives a domain reload), registers a passive default control so clicks on empty space cannot deselect the player, and writes only through a `SerializedObject` for Undo and prefab overrides. It only edits `AnchoredPosition` / `LocalPosition` on a player outside play mode. It draws from the rest state and the step's simulated start (`UIAnimationSimulation`), so a path in a later step starts where the earlier steps leave the object, and it keeps drawing through a preview — it used to draw from where the object sat, and paused while previewing, which read as the path vanishing on Play. The gizmos skip the step it is editing.

DOTween behaviours worth knowing, all silent when violated: `SetLink` is a no-op on a tween inside a Sequence (apply it to the outer `Sequence`); a tween must be configured fully *before* `Append`/`Join`, since `DoInsert` sets `creationLocked` and `From`/`SetEase`/`SetRelative` then do nothing; `.From(value)` defaults to `setImmediately: true` and writes during construction rather than at t=0; a stencil `Mask` defeats material instancing because `StencilMaterial.Add` caches a copy that never re-syncs (`RectMask2D` is fine, and `MaterialPropertyBlock` does not work with UGUI at all); `TextMeshProUGUI` ignores `Graphic.material`, so use `TMP_Text.fontMaterial` and never destroy it. `SetUpdate(true)` is required for UI that animates while `Time.timeScale == 0`.

**DOTween's kill semantics differ between play mode and edit mode, and this will make an edit-mode test lie.** Measured against DOTween 1.3.030 in Unity 6000.3:

| | `tween.Kill()` | `DOTween.Kill(id)` / `KillAll()` / `Clear()` | `Pause()` | `Complete()` |
| --- | --- | --- | --- | --- |
| Play mode | despawns immediately, `OnKill` fires | same — immediate, `OnKill` fires | works | `OnComplete` then `OnKill`, both immediately |
| Edit mode | **nothing** — `IsActive()` stays true, `OnKill` never fires | **work** — the tween goes inactive | works | works, both fire |

The cause: **DOTween never initialises out of play mode** (`DOTween.initialized` stays false; its init check bails on `!Application.isPlaying`), and `Tween.Kill()` returns early when it is not initialised. The filtered operations behind `DOTween.Kill(id)` / `KillAll` have no such check. **A test that kills a tween out of play mode and asserts on the result is measuring the Editor, not the game.** This cost a wrong conclusion once: `OnKill` was written off as never firing for a plain `Kill()`, and a polling `Update` was added to work around a problem that does not exist in a build. Check tween lifetimes in play mode.

It also cost a real bug in the edit-mode preview, because **`DOTweenEditorPreview.Stop()` does not kill either** — it only stops calling `DOTween.ManualUpdate`. A stopped preview's sequence stayed active and *playing*, so the next preview's update loop resumed it alongside the new one, replaying its callbacks: "Stop and Restore" appeared to work (values restored) and the next Play then continued every old preview from where it left off. That is why `UIAnimationPreview` tags every sequence with an id, pauses it and kills it with `DOTween.Kill(id)`.

Separately: **`DOTween.Kill(x)` matches by a tween's *target or id*, so `DOTween.Kill(sequence)` matches nothing and is a silent no-op** — it is not the same call as `sequence.Kill()`, despite reading like it.

## FlipbookAnimation

No dependencies — not even DOTween. It only writes `Image.sprite`, so DOTween can move, scale and fade the same object at the same time; that split is intentional.

`UISpriteFlipbook` cycles an `Image` through a list of sprites. `UIFlipbookSelectable` sits *beside* a `Selectable` and picks the clip for its interaction state (Disabled > Pressed > Selected > Highlighted > Normal, matching Unity's own priority), leaving `onClick`, navigation and transitions untouched. `UIFlipbookClipAsset` is an optional ScriptableObject for sharing one clip across many objects.

Per clip: frames, FPS, loop mode (`Once` / `Loop` / `PingPong`) and timing mode (`Constant FPS` / `Random Offset` / `Per Frame Durations`).

Things that look wrong but are intentional:

- **A clip that merely ran out is not the same as one that was `Stop()`ped, and `OnEnable` tells them apart via `stoppedExplicitly`.** `Stop()` sets it, completion does not, `Play()` clears it. Without this a `Once` clip plays exactly once per scene load, and a panel shown, hidden and shown again sits frozen on its last drawing.
- **Randomised frame timing is rolled per pass on the *player*, never on the clip.** One clip asset can drive hundreds of objects, and rolling on the clip would give them all identical timing — the exact thing randomising was meant to prevent. `RandomStartFrame` lives on the player for the same reason.
- **Ping-pong turns at `count - 2`**, not `count - 1`, so the end drawings are not held for a double beat. A 4-frame clip reads `ABCDCBABCDCB`.
- **`Selected` deliberately does not fall back to `Highlighted`.** A button keeps EventSystem selection after a click, so borrowing the hover look while the mouse is elsewhere reads as a stuck button. An empty `Selected` means "no focus look".
- **Do not set the Selectable's Transition to `Sprite Swap`** — it writes `Image.sprite` itself and fights the flipbook. `OnValidate` warns about it.
- **`LoopMode` replaced a serialized `bool Loop`, and Unity cannot convert between them.** `MigrateLoop()` reads the legacy bool once, using the older `defaultsFilled` flag to tell authored data from a zero-filled new element. Both hidden fields must stay for any project still holding pre-migration assets.
- Sprite thumbnails use `GUI.DrawTextureWithTexCoords` over `sprite.textureRect` rather than `AssetPreview`, which loads asynchronously and returns null on the first repaints.
- The frame sort is numeric-aware, so `frame_2` precedes `frame_10` and `frame_007` lands beside `frame_7`.

## SelectableEvents

The project author's own code. `SelectableEvents` exposes UnityEvents for hover, unhover, press, release, click, select, deselect and submit on anything deriving from `Selectable`.

It implements the same EventSystem handler interfaces as `UIFlipbookSelectable`, and **that is fine** — the EventSystem delivers each event to *every* handler on the object, so both receive it and the Selectable's own behaviour is unaffected. Note the asymmetry in its guards: `OnHover` and `OnUnhover` fire regardless of `IsInteractable()`; press, click and submit do not.

## Shared conventions in the Claude-authored tools

Both use the same patterns, and anything added to them should too.

**Inspector-authored data classes need a `FillUnsetDefaults()` called from the owner's `OnValidate`.** Unity does not run C# field initialisers for elements added with `+` on a serialized `List<T>` — a new element is zero-filled, so `= 12f` / `= true` silently do not apply. `FillUnsetDefaults` only writes fields still at their zero value, so authored data is never clobbered. Where `false` is both "never set" and "the user unticked it", a hidden `defaultsFilled` bool is what distinguishes them.

**Serialized enums are stored as integers, and those integers are the contract.** Every enum here assigns its values explicitly (`Scale = 12`) so reordering the lines is harmless. *Changing* a number, or reusing a retired one, repoints every asset authored against it with no error and no warning. This cost a day once: alphabetising `UIAnimationStepType` turned 16 authored `Scale` steps into `GraphicAlpha` steps and faded a menu to invisible. It reads like lost references or a corrupt prefab, so **if animations "disappear", check the enum's history before blaming the asset** — the fix is to remap the stored integers, never to reorder the enum back. Any new Inspector-authored enum should assign its numbers explicitly from the start.

**Edit-mode preview animates real scene objects, and three things make that safe.** Both tools have one; all three mechanisms are load-bearing. Capture before and restore after, *per property* — never a blanket `EditorJsonUtility` round-trip of the component, which also rewrites object references and blanks things like an `Image`'s sprite. Re-capture baselines before *every* preview, so relative endpoints do not drift on repeats. Clear callbacks, because an `On Complete` UnityEvent is wired to arbitrary game code that must not run outside play mode. Plus: only one preview at a time (that is what guarantees the captured state belongs to the object being restored — the DOTween preview chains animations *within* one player, see its entry), one `Undo` entry as a backstop, `EditorUtility.SetDirty` on each touched object, and an unwind on selection change (the DOTween preview waits until the selection leaves the player and everything it animates — see Use Current), play-mode change and assembly reload — registered from an `[InitializeOnLoad]` static constructor, not left to an inspector's `OnDisable`. And make sure a stopped preview is actually *dead*: out of play mode the ordinary DOTween kill does nothing (see the DOTween table).

**Right-click menus are scoped by target object, not by type name.** `SerializedProperty.type` and `propertyPath` report *unqualified* names, so a namespace does not disambiguate them and another project's `UIAnimation` or `Frames` list would match a string comparison — require your own component as `serializedObject.targetObject` instead. Also `.Copy()` the property handed to the callback, since menu items run after it goes out of scope, and register `contextualPropertyMenu` **once per folder**: every handler appends to the same menu.

**When copying Inspector data, use `JsonUtility`, not `EditorJsonUtility`.** Despite the names, the plain one preserves `UnityEngine.Object` references (`{"instanceID":-228892}`) and the Editor one destroys them (`{"instanceID":0}`), because it serializes the way an asset file does, where a reference is a file ID an in-memory scene object does not have. This was backwards once and dropped every target slot on paste.

**Two Unity API limits these tools work around.** `[Range]` clamps typed input as well as the slider, so it cannot express "the slider stops at 12 but you may type 24" — draw the slider and the field separately, and only adopt the slider when it actually moved. And `GetPropertyHeight` is not given the width it will be drawn at, so a drawer whose height depends on wrapping has to find it another way. The step drawer's warning row does it with `EditorGUIUtility.currentViewWidth`, which *is* live there: everything between the view's edge and the drawer (Inspector margins, list handles and padding) is a fixed number of points, so `OnGUI` records `currentViewWidth - position.width` per property path (skipping `Layout` events, whose rect is a dummy) and the measuring pass lays out at `currentViewWidth` minus that. It matches the draw to the point and follows a window resize with no lag — checked by screenshot at 320 / 420 / 760 px, three / two / one lines. A new view's first measure uses a guessed margin; `ReorderableList` re-measures on its first repaint anyway (a changed list rect invalidates its height cache), and `OnGUI` calls `HandleUtility.Repaint()` whenever the recorded margin changes. Anything that does not wrap should still use a fixed number of rows and truncate, like the step header.

**Testing enable-time logic requires reflection.** Edit mode does not deliver `Awake` / `OnEnable` / `OnDisable` to a component without `[ExecuteAlways]`, so a test that toggles `SetActive` exercises nothing and quietly passes. Invoke the callback directly instead. The mirror-image trap: in *play* mode `AddComponent` runs `Awake` immediately, so a test that fills in serialized fields afterwards is talking to a component that has already initialised against empty ones. Reset the lazy-init flag as well as setting the field.

## Verifying a change

**This repo is loose drop-in folders, not a Unity project** — no `Assets/`, no `ProjectSettings/`, no Editor to compile against. Nothing here can be claimed to compile without actually compiling it somewhere else.

The recipe that works: copy the tool folder into a real Unity project that has DOTween Pro, under a temp path like `Assets/_CompileCheck/`, **without the `.meta` files** so it cannot collide with an existing copy's GUIDs; compile; delete the folder afterwards and recompile so no stale assemblies are left. `GameCraftSep2026Jam` has DOTween Pro and holds older *un-namespaced* copies of these tools, so a staged `rmf_claude.DOTweenUI` copy sits beside them without conflict — that separation is what makes it usable as a host. Ask before using a different project.

**The strongest available regression test is a fingerprint diff against a real project's authored animations, and it is cheap.** `GameCraftSep2026Jam`'s `UIAnimatorTest` branch holds a copy of these tools under `Assets/Scripts/UI/Utility/DOTweenAnimationPlayer/` whose `.cs` files are identical to the library apart from **two header-comment lines** (the host copy says "Not hand-written by the Twindrill Goose team", which was deliberately removed from the library) and line endings, which git's autocrlf rewrites on any checkout or stash — compare with `tr -d '\r'`. Upgrade it in place: overwrite the `.cs` files **but keep the host's first seven header lines** (`head -7` of the host file + `tail -n +8` of the library file), **keep the project's existing `.meta` files** so prefab GUIDs survive, and let Unity generate metas for genuinely new files — then copy that generated meta back into the library so both share the GUID. Then, in play mode, walk every `UIAnimationPlayer` in the scene, `Play` each animation, `Goto` five points across its duration, and write out every scene property that moved away from rest. Do that before and after and diff the text. Two things that make the fingerprint trustworthy: **build a fresh sequence per sample point** (rewinding one sequence accumulates on any relative or `To: Current` step, which is a property of `Goto`, not of the animation), and **run it twice before trusting it** to prove it is deterministic. Enumerate names through `EditorCollectAnimationNames`, not `EditorAnimations`, or a player that moved to a shared asset reads as empty.

**When a change only touches target resolution or baselines, a cheaper edit-mode diff is enough and needs no play mode.** Call `EditorPrepareForPreview()` on every player in the scene and dump, per runtime step, the private resolved-target fields, `targetPathMissed` and the baseline fields by reflection, plus any warnings logged. Take it on the new code, then `git stash push -u -- Assets/Scripts/UI/Utility/DOTweenAnimationPlayer` in the host (the `-u` matters: an untracked new file that uses new APIs would otherwise break the old code's compile), recompile, dump, `git stash pop`, recompile, and diff. Keep the dump harness compatible with both versions — reflection only.

**The cleanest play-path fingerprint needs no play mode and never touches the user's scene.** Instantiate `Assets/Prefabs/UI/UI.prefab` into an additive scratch scene (`NewScene(..., Additive)`), and for every player and animation, six times per animation: `EditorPrepareForPreview()`, `Random.InitState`, `player.Play(name)`, `DOTweenEditorPreview.PrepareTweenForPreview(seq, true, true, false)`, one `DOTween.ManualUpdate(t, t)` to the sample point, dump the targets, then `DOTween.Kill(id)` / `StopAll()` / `EditorRestoreBaselines()`. It calls `Play` directly, so it measures `BuildSequence` / `BuildTween` and nothing the preview adds, and it uses only APIs every version has. It is how the `LayOutSteps` extraction was proven byte-identical (30 animations, 180 samples, deterministic across two runs).

**A cheap behavioural fingerprint also runs in edit mode, through the preview.** Since preview `Play` applies the From state first, this one now differs from play mode for animations with `ApplyFromValuesImmediately` off — use the direct play-path fingerprint above for anything about runtime behaviour. For every player and animation in the scene: `UIAnimationPreview.End()`, seed `Random.InitState` (shake is random), `UIAnimationPreview.Play`, read the sequence out of the private static `running` by reflection, then `DOTween.ManualUpdate` through five equal slices of its duration, dumping every target's properties after each. Old vs new via the same stash procedure; it needs only APIs both versions have. It exercises `BuildSequence` / `BuildTween` exactly as play mode would, and it is how the Snapping and punch/shake change was proven byte-identical on the 33 animations in `UI.unity`. It does not cover anything play-mode-only (lifetimes, `OnKill`).

**`GameCraftSep2026Jam`'s `Assets/Scenes/UI/UITester.unity` and `UITester2.unity` hold the hand-test stations** (`UITester2` for the gizmos, the type check, Use Current and the CloseCredits replica, with a shared asset beside it) — a labelled grid under `UI/UIAnimation Tests`, one player per station — so the author can test by selecting objects rather than setting things up. It was built by a throwaway builder harness that opens the scene *additively* (`EditorSceneManager.OpenScene(path, OpenSceneMode.Additive)`), builds, `SaveScene`s it and closes it again, which leaves the user's open scene — often dirty with their own work — untouched. Never open a scene in `Single` mode from a harness: it discards the open scene's unsaved changes without asking.

**Edit-mode preview can be tested without waiting on editor frames.** Every preview sequence is `UpdateType.Manual`, so a harness can call `UIAnimationPreview.Play` and then drive time itself with `DOTween.ManualUpdate(dt, dt)` in a loop, all inside one `eval`, in an additive scratch scene. That is exact and repeatable where sleeping between `eval` calls is not — the round trip is long enough to swallow a whole 0.6s animation. For things only the real editor does (entering play mode), start the preview in one `eval` and use `editor_play` / `editor_stop`; a plain `object` as the requester keeps any inspector's `OnDisable` out of the result.

A namespaced library dropped into an un-namespaced project needs a `using` in any game code that references it — one file in that project. Serialization does not care: the `.meta` GUID is the script reference, so changing a class's namespace while keeping its GUID leaves every prefab intact.

That editor is reachable from the `unity` CLI: `unity cmd recompile` then poll `unity cmd recompile_status`, which is authoritative — the console buffer replays stale entries and will show you errors you already fixed. `recompile` itself usually reports a **network error**: the domain reload drops the connection mid-request, and that is expected, not a failure — poll the status. `unity cmd eval` runs C# against the live Editor, which is how behaviour (not just compilation) gets checked; put anything longer than a few lines in a compiled harness class and call it from `eval`, because the eval wrapper mangles long scripts. **Eval code cannot carry `using` directives**, so DOTween's extension methods (`SetEase`, `Goto`, `Kill`) have to be called statically (`DG.Tweening.TweenExtensions.Goto(t, 0.5f)`) or from a harness. `unity cmd editor_play` / `editor_stop` switch modes, and per the DOTween table above, **anything about tween lifetimes has to be checked in play mode.** A harness lives in a temp folder such as `Assets/_PathCheck/Editor/` and is deleted (with its `.meta`) and recompiled away at the end.

Checking editor UI (drawers, Scene-view handles) needs a real picture, and two obvious routes do not give one. **`capture_scene_view` renders only the camera — no handles, gizmos or overlays** — and it saves under `Assets/` (a relative `Temp/x.png` becomes `Assets/Temp/x.png`, a new folder in the host project to clean up). What works is a Win32 `PrintWindow(hwnd, hdc, 2)` of the Unity window from PowerShell, which captures a DX12 window without bringing it to the front; call `SetProcessDPIAware()` first or the capture is clipped at 125% scaling. Look the window up with `FindWindow([NullString]::Value, title)`: PowerShell turns a plain `$null` into `""` for a string parameter, and `FindWindow("", title)` finds nothing. The main window's Inspector can run off the edge of the monitor, so to see a property drawer, open a temporary utility `EditorWindow` that draws the property with `EditorGUILayout.PropertyField` and capture that window by title. Scene-view *interaction* can be driven with `SceneView.SendEvent`: a Layout pass runs before each event, but window coordinates arrive shifted into the camera clip (about 50 points in y), so calibrate the offset with one `MouseMove` and a `duringSceneGui` probe before clicking. Put throwaway test objects in an additive `EditorSceneManager.NewScene(..., Additive)` and close it with `CloseScene(scene, true)`, so the user's open scene is never touched. **Scene-view gizmos can be screenshotted** with a floating `SceneView` (`CreateInstance<SceneView>()`, a unique `titleContent`, `ShowUtility()`, `Frame(bounds)`) captured by that title — but every Screen Space Overlay canvas sits at the same world position, so the user's open scene draws on top of the test scene; `SceneVisibilityManager.instance.Isolate(go, true)` shows just the station, and `ExitIsolation()` afterwards. **`Selection.selectionChanged` does not fire while the Editor is in the background** — a harness that sets `Selection.activeObject` and waits sees nothing happen, however long it waits (`InternalEditorUtility.isApplicationActive` is false). Fire the delegate yourself (`typeof(Selection).GetField("selectionChanged", …).GetValue(null)` → `DynamicInvoke`) and then `ActiveEditorTracker.sharedTracker.ForceRebuild()`, which is what a click in the foreground does. One tooling trap: the Bash tool turns `\\$2` in a script into `$2` literally — build Windows paths with `cygpath -w "$dir/$name"` instead.
