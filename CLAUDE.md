## The UI tools in this project

Three reusable UGUI tools, each a self-contained folder with its own `README.md`. **Read the relevant README before changing a tool** — for `DOTweenAnimationPlayer`, read the wiki instead (below). They are independent — no tool references another.

**`DOTweenAnimationPlayer`'s user docs live in the GitHub wiki** (September 2026, on request; the README had grown to 940 lines): `https://github.com/rmfandyplayz/UnityUIAnimationTools.wiki.git`, pushable with the author's normal git login. Its README now holds only a short install note, the Code API signature block and a link. **A change to the public API must update both the README's block and the wiki's `Code-API.md`.** Any user-visible behaviour change goes into the relevant wiki page. Wiki conventions: plain language written for non-programmers first; technical detail in a collapsed `<details><summary><b>Under the hood</b></summary>` block (blank line after `</summary>`, or its markdown doesn't render); GitHub alerts (`> [!TIP]`, `> [!WARNING]`, `> [!NOTE]`) for tips and traps, which the wiki does render; no `# Title` line, since the wiki already shows the page name; step types by their Inspector names (`Anchored Position`, not `AnchoredPosition`); links as `[text](Page-Name#heading-slug)`. Navigation is `_Sidebar.md`, in six sections (Installation, Code API, Basic usage, Advanced usage, Nitty-gritties, Warnings and Gotchas) under a "UI Animation Player" heading, leaving room for the other tools later. Check links resolve before pushing: every `(Page#anchor)` should match a file and a heading slug.

| Folder | What it does | Namespace |

Common to all three: runtime types are `public`, editor-only drawers and custom editors are `internal`, and the `.meta` files carry the script GUIDs — **a folder copied without them loses every component on existing prefabs.**

**`DOTweenAnimationPlayer/` is a UPM package; the other two are still loose folders** (since September 2026, on request, so projects can update it from Package Manager). Projects install it by git URL, `https://github.com/rmfandyplayz/UnityUIAnimationTools.git?path=/DOTweenAnimationPlayer#vX.Y.Z`, and update by changing the tag (the wiki's `Installation.md` walks users through it). **To release**, when the author asks:

1. `git status` first: any new file or folder under `DOTweenAnimationPlayer/` needs its `.meta` committed (see below).
2. Bump `version` in `package.json` (semver: patch for fixes, minor for additions, major for anything that breaks saved data or the public API).
3. Change `#vOLD` to `#vNEW` in the install URL in `DOTweenAnimationPlayer/README.md` and in the wiki's `Installation.md` (step 4, and the example in Updating).
4. Commit, then `git tag -a vX.Y.Z -m "vX.Y.Z"`, and ask before pushing. Push the commit *and* the tag (`git push origin main vX.Y.Z`): a git-URL install reads the tag, so a release without it doesn't exist. Push the wiki too.
5. Projects move by editing the tag in their `Packages/manifest.json`. `GameCraftSep2026P2Jam` is pinned by git URL, so update it only if asked. The jam's `file:` link needs nothing.

A pushed tag is what projects install. Don't move or delete one; release a new version instead. What the package needed, and why:

- **Two asmdefs**, `rmf_claude.DOTweenUI` at the root and `rmf_claude.DOTweenUI.Editor` in `Editor/` (Editor platform only). A package's scripts are only compiled inside an asmdef. Inside one, a folder named `Editor` is no longer special, and the second asmdef is the only thing that keeps editor code out of builds. Both are `autoReferenced`, so game code in `Assembly-CSharp` sees the tool with no change.
- **They reference `DOTween.Modules`, which exists only after DOTween's Utility Panel → Create ASMDEF.** DOTween's UI shortcuts (`DOAnchorPos`, `DOFade`, `DOColor`, `DOSizeDelta`, punch/shake anchor pos) are *generated* into `Assets/Plugins`. Without that button they compile into the predefined `Assembly-CSharp-firstpass`, which no asmdef can reference. **This is why there was a "never add an asmdef" rule before, and it still holds for any copy that is not the package:** an asmdef with no `DOTween.Modules` to reference loses every one of those shortcuts. Forgetting the click gives exactly 7 errors (CS1061 / CS1929) in `UIAnimationStep.cs`, measured. None of them names the cause, so the README names them. **A setup check inside the package cannot help**: Unity loads no new code from a package that fails to compile, so the check never runs. Swapping the 7 shortcuts for DOTween's core calls (`DOTween.To` / `ToAlpha` / `Punch` / `Shake`, which is all the module does) would remove the click entirely. It was declined: `DOShakeAnchorPos` also calls `SetSpecialStartupMode`, a helper DOTween exposes only for its own modules, so a DOTween update could rename it together with its modules and break us.
- **Every folder needs a committed `.meta`.** A git-installed package is read-only, and Unity *ignores* an asset in it that has no meta. After the September reorganisation the subfolders (`Attributes/`, `Data/`, `Helpers/`, `Editor/*/`) had none in the repo, which would have silently dropped every script in them. New files also need their meta committed. The easy way to get one is to let the jam's `file:` link (below) generate it.
- `package.json` says `"unity": "2022.3"`, because `SerializedProperty.boxedValue` needs 2022.1+. The README used to claim 2021.3.
- **Moving into the asmdef did not break UnityEvent listeners** that store the old `m_TargetAssemblyTypeName: UIAnimationPlayer, Assembly-CSharp` (not even namespaced). Measured in the jam: all 32 listeners on tool types in `UI.prefab` and both tester scenes still resolve through `UnityEventBase.FindMethod`, the call runtime uses.

`FlipbookAnimation/` and `SelectableEvents/` are unchanged: no asmdef, and the `Editor/` folder name is what separates their editor code.

## DOTweenAnimationPlayer

Requires **DOTween Pro**. After importing it, run `Tools → Demigiant → DOTween Utility Panel → Setup DOTween…` and then **Create ASMDEF** in the same panel (see the package notes above). Neither is optional, and neither is the same as importing DOTween. Skipping either produces errors pointing at *this* code rather than the real cause.

**Layout** (reorganised on request, September 2026; the author wanted the folder less crowded): `UIAnimationPlayer.cs` and `UIMaterialInstance.cs` stay at the top as the two components you add. `Data/` holds `UIAnimation`, `UIAnimationStep` and `UIAnimationAsset`; `Helpers/` holds `UIAnimationAudio`, `UIAnimationProperty`, `UIAnimationSteppedEase` and `UIAnimationLog`; `Attributes/` holds the four `PropertyAttribute`s. Under `Editor/`, `UIAnimationTargets.cs` stays at the root (everything uses it), with `Inspectors/` (player and asset editors, Shared Animations, the preview), `Drawers/`, `SceneView/` (gizmos, path editor, simulation) and `Menus/` (context menu, mirror, Save as Animation Set). The author moved the files by hand, every one with its `.meta`, so no GUID changed; any folder under one named `Editor` is still editor-only.

**The jam's copy and the library now share every script GUID, and they didn't until September 2026.** Three had drifted apart: `UIAnimationAsset`, `UIAnimationAssetEditor` and `UIAnimationPreview`. The library and `GameCraftSep2026P2Jam` agreed (P2's `CountNumber.asset` uses the library's `UIAnimationAsset` GUID). The jam differed, and its five test sets pointed at the jam's own. When the author copied the reorganised library over the jam, metas included, every set in the jam lost its script and every shared animation broke. The fix repointed those five sets' `m_Script` at the library GUID, one line each. Nothing else in the jam, on any branch, referenced the old `UIAnimationAsset` GUID, and nothing references an editor script's. **If Animation Sets "break" after copying the folder anywhere, compare script GUIDs before anything else.**
`UIAnimationPlayer` holds a list of named animations, each a list of steps, and plays them: `player.Play("Show")`. A step drives one property on one target — anchored position, scale, rotation, colour, alpha, size delta, offset min/max, material float/colour, `SetActive`, punch (position, rotation, scale), shake (position, rotation, scale), a sound, or — `CustomProperty` — any public float / int / Vector2 / Vector3 / Color / string member of any component, picked from a dropdown and driven by `DOTween.To`. Steps run in sequence or joined to the previous one, with per-step delay, duration, ease and endpoint mode (`Absolute` / `Baseline` / `Current`). It is deliberately generic and knows nothing about menus, HUDs or transitions — **do not add game-specific logic to it.**

Five things are optional and invisible when unused, and an existing player with none of them behaves exactly as it always did: a shared `UIAnimationAsset` in the player's `Shared` slot, a `TargetPath` on a step, the `Play(string, Action<UIAnimationEndReason>)` overload, an animation's own Snapping (one DISABLED / ALL STEPS / PER STEP button in the Inspector, the two bools `Snapping` / `SnapPerStep` in code), and a step's movement path (the `Custom Path` dropdown in the Inspector, `UseCustomPath` + `PathShape` in code, which routes a vector step through waypoints to `To`, with a Scene-view handle editor in `Editor/SceneView/UIAnimationPathEditor.cs`). The path was added with a before/after fingerprint of every authored animation in `GameCraftSep2026Jam`, which came out byte-identical. Everything else added since is editor-only and cannot change playback: the Scene-view gizmos, the Inspector's type check and its Use Current Value button. The one exception is the `CustomProperty` step type, which is additive rather than optional: a new enum number (20), new fields that every other type ignores, and a new `case` in each switch. No existing step can reach its code, and the fingerprint agrees: `UI.prefab`'s play path came out byte-identical before and after.

Two more were added in September 2026 on the same terms. **From / To set from code** (`SetFrom` / `SetTo` / `ClearOverrides` on the player) is invisible when unused: nothing stores anything until it is called. **Interrupt Others' two buttons** (`CompleteInterrupted` / `CompleteSilently`, STOP / COMPLETE and REPORT / SILENT) are additive: both bools read false on anything authored before them, and false/false is the old stop-where-it-stands path, byte for byte the same loop. Both went through the play-path fingerprint: `UI.prefab` plus copies of both tester scenes, 71 animations and 426 samples, byte-identical before and after and deterministic across runs. A play-mode harness then checked every interrupt mode and every `SetTo` / `SetFrom` kind, 62 checks, all passing. **One deliberate behaviour change came with them, on request:** `Stop(name, complete: true)` and `StopAll(true)` now finish through the same path as COMPLETE REPORT, so they run the `SetActive` steps they used to skip (see `Finish` below). Nothing in either tool or the jam called them with `true`.

**Shared Animations and each player's own On Complete** (late September 2026) are additive the same way: a hidden `Id` string on `UIAnimation` (empty on everything authored before it, and on any animation no player has given an On Complete), a hidden `SharedOnComplete` list on the player (empty), and a `[NonSerialized] PlayerOnComplete` on a player's clone of a set's animation, null unless an entry matches. With neither filled, `BuildRuntimeList` and both On Complete call sites do exactly what they did. **One more deliberate behaviour change came with them, on request: a punch or shake that `Kill` stops part way is put back where it started** (see `SettleImpulse` below). The play-path fingerprint was not rerun for this batch, since nothing in `BuildTween` changes a value; it was checked in play mode instead (punch spam settles at 1.000, shake at 0, each player's On Complete fires after the set's, the type check runs against the viewing player).

Things that look wrong but are intentional:

- **Reversing is an authoring operation, not a playback mode.** `Mirror Animation` / `Duplicate as Mirrored` rewrite the data once, so a mirrored `Show` is a real, editable `Hide`. There is no runtime `PlayReverse`, and **there should not be** — a live reverse mode and an authored mirror are two answers to the same question, and having both was tried and cut.
- **Mirroring deliberately does not touch easing** — neither the `Ease` preset nor a custom curve. The house style is that things decelerate into place in *both* directions, so a mirrored `Hide` keeps the `Out` ease its `Show` was authored with. Ease inversion was built, then removed on request. Do not reintroduce it.
- **`PlayAnimation` / `StopAnimation` are not redundant wrappers around `Play` / `Stop`.** Unity's UnityEvent dropdown only lists methods returning void with at most one argument, which excludes `Play` (returns a `Sequence`) and `Stop` (an optional parameter reads as two overloads). A void `Play(string)` cannot be an overload — C# does not overload on return type.
- **Stepped playback ("Play At Custom FPS") is implemented on the ease, not on the clock.** It quantises the *time* handed to the underlying ease, so the tween still updates every frame but holds its value between boundaries. Every step shares one grid keyed off its absolute sequence position — per-tween grids read as jitter. Punch and shake are excluded because they drive their own oscillation.
- **`WithPrevious` steps are groups, not rows.** Anything reordering a step list must keep each group's members together and contiguous, or it silently re-parents which steps are joined to which.
- **`AnchoredPosition`, `SizeDelta`, `OffsetMin` and `OffsetMax` all write the same rect.** Unity stores one rect and derives every view from it, so animating two of them on one target makes them overwrite each other. Any new rect-driving step type must also be added to `CaptureBaseline`, or `To: Baseline` collapses the target to zero.
- **A step's `Delay` is applied in exactly one place: the insert position `BuildSequence` computes.** `BuildTween` must never call `SetDelay` — DOTween adds a tween's own delay *on top of* its sequence position, so doing both doubles every delay. This regressed once already.
- `UIAnimationAudio.Shared` is the one global in the folder. For a mixer, call `UIAnimationAudio.SetShared` once rather than adding another.
- **A player deep-clones every animation it takes from a shared `UIAnimationAsset`, and that is correctness, not caching.** `RuntimeSequence`, `RuntimeCallback` and each step's resolved targets (`rect`, `graphic`, …) are ordinary instance fields on `UIAnimation` / `UIAnimationStep`, so two players reading one asset would overwrite each other's live sequences and animate each other's objects. `CloneForRuntime` round-trips through `JsonUtility` and then re-points `OnComplete` at the *original* `UnityEvent` rather than copying it — a persistent-call list is Unity's own serialization detail and a listener list is read-only at runtime. Consequence to keep documented: editing an asset at runtime does not reach players that have already initialised, and assigning `Shared` from code after `Awake` does nothing.
- **`TargetPath` reaches upward as well as down, because `transform.Find` accepts `..`.** Measured in Unity 6000.3: `Find("..")` returns the parent and `Find("../../Name")` walks up twice then down. This is not a curiosity — the common authoring layout puts the player on a child object called `Animations` and drives the *button above it*, which is not a descendant and would otherwise be unshareable. `..` is what makes that layout portable, so do not "fix" `ResolveHost` by restricting it to descendants. Segments resolve one at a time, so `../Self` means "a child of my parent with that name", not "me".
- **A `TargetPath` that matches nothing resolves the target to null, not to the owner.** A step that visibly does nothing is far easier to diagnose than a mistyped `Panel/Icon` quietly scaling the whole panel. `ResolveHost` warns once from `Resolve`, and sets `targetPathMissed` so `HasTarget` does not warn a *second* time on every `Play` — the same precedent the shader-property check already set.
- **The end-callback fire-once flag is a local captured by each play's closure, never a field on the animation.** An `onEnd` that plays the same animation again re-arms the animation while the old play is still tearing down; a guard living on the animation would then let the old play's teardown fire the new play's callback. For the same reason `Kill` only clears `RuntimeSequence` / `RuntimeEndCallback` when they still `ReferenceEquals` the ones it started with.
- **A kill the player did not issue is caught by the sequence's own `OnKill`, and the player deliberately has no `Update`.** `PendingEndReason` carries the reason into that callback: armed as `Stopped`, overwritten by `Kill` before it kills. Every end path therefore has two routes to the same callback — the synchronous invoke in `Kill` and DOTween's own — and the fire-once flag makes whichever arrives second a no-op. A polling `Update` was written first, on a measurement that turned out to be an edit-mode artifact; see the DOTween table below before reaching for one again.
- **Destroying an *enabled* player reports `Disabled`, not `Destroyed`.** Unity runs `OnDisable` before `OnDestroy` and offers no way to know a destroy is coming. That is reported honestly rather than guessed at with heuristics like `scene.isLoaded`; `Destroyed` is what you get when `KillOnDisable` is off or the object was already inactive.
- **`UIAnimationEndReason.NotFound` is deliberately a reason rather than a silent no-callback.** A mistyped animation name is a production runtime failure, and the whole point of that overload is that a caller is never left waiting.
- **A From / To set from code lives in `[NonSerialized]` fields beside the authored value, never written over it.** For a *local* animation the runtime step *is* the serialized one, so writing into `ToFloat` would change what the Inspector shows in play mode and leave `ClearOverrides` nothing to go back to. Every playback read goes through `FromVectorValue` / `ToFloatValue` / …, which return the authored field when nothing is set. There is one slot *per value kind* (`EndpointOverride`), so a step whose Type changes afterwards never reads another kind's leftovers. The value keeps the step's mode (a Baseline To is still rest + value). `SetFrom` refuses a step whose From is off rather than storing something that would do nothing. Steps are addressed by index because a step has no name; the README warns that reordering changes the numbers. Shared-set animations are per-player clones, so an override never reaches another player. One consequence to keep in mind: the edit-mode preview's `EditorPrepareForPreview` re-clones shared animations, dropping any override on them. Nothing in edit mode sets one.
- **Every "end it at its end state" path goes through `Finish`, never DOTween's `Kill(complete: true)`** — Interrupt Others' COMPLETE, `Stop(name, complete: true)` and `StopAll(true)`. DOTween's `Kill(complete: true)` completes *without* a Sequence's internal callbacks — **measured in play mode, 6000.3 / DOTween 1.3.030**: the position reaches its end and `On Complete` fires, but a `SetActive` step still ahead never runs. `Stop(complete)` used it until September 2026 and had exactly that bug. `Finish` calls `Complete(true)` instead (the same call the preview's `FinishRunning` uses), which does run them, and sets `finishing` so the sound callbacks it passes stay quiet. SILENT nulls the sequence's `OnComplete` first, so `OnKill` reports the caller's reason. The player's own `Kill` therefore only ever stops where it stands and no longer takes a `complete` flag.
- **`FinishRunning` snapshots who is running, sequence and all, before finishing any of them, then sweeps with a plain stop.** It serves COMPLETE (skipping the animation being played) and `StopAll(true)` (skipping nothing). REPORT runs `On Complete`, which can chain into another animation on the same player. Finishing whatever is live *during* the loop would then complete a chain to its end or not, depending on list order. The snapshot finishes only what was running when the call was made. The sweep stops anything the callbacks started, the animation being played included, before its sequence is built — and for `StopAll(true)`, so nothing is left running at all.
- **Playing an animation that is already running always stops it where it stands, whatever its own STOP / COMPLETE says** — those buttons are about the *others*. (A punch or shake caught part way is put back where it started; see the next entry.) Completing first would snap a step with no From to its end, so a replay would do nothing visible. This was questioned in September 2026: the N2 coin test read the half-counted number on screen as the total, so spam-clicking added less than 7 a click. The fix was the test keeping its own total (README: keep the real total in your code and `SetTo` it). The rule stayed, with a line added to the tooltip and README.
- **A punch or shake that `UIAnimationPlayer.Kill` stops part way is put back where it started** (`UIAnimationStep.SettleImpulse`, on request, September 2026). DOTween's punch and shake are relative to the value at their start (`SetPunch` adds it to every point), so one stopped mid-wobble stayed displaced and the next wobbled around that: three presses of N1's Interrupt buttons 0.1 s apart left the runner at 2.19x (measured before; 1.000 after). The start is read in the nested tween's `OnStart`, which DOTween runs before writing anything and once per lifetime — fine for loops, since a punch's points are fixed at its first startup. `Kill` writes it back only when `ElapsedPercentage(false)` is strictly between 0 and 1, last step first so where two overlap the earlier start wins. The target and type are pinned at build time, like `baselineType`. `BuildTween` forgets the tracked tween before anything else, because DOTween may reuse a dead tween's object. `Finish` needs nothing: a completed punch ends on its start.
- **`CompleteInterrupted` defaults to true only for a never-filled animation** (`Loops == 0 && Name` empty in `FillUnsetDefaults`), not through its initializer. Unity gives a field missing from old data its initializer value. False has to mean "authored before this existed", or every existing animation would switch to COMPLETE on load. This relies on `+` on an empty list zero-filling. That was measured in 6000.3, through both `arraySize++` and `InsertArrayElementAtIndex`: every field arrives at zero, bools included, and `ApplyModifiedProperties` runs `OnValidate`. **That zero-fill also means `InterruptOthers` and `ApplyFromValuesImmediately` used to arrive *unticked* on a new animation, despite their `= true` initialisers.** The same never-filled branch now sets both to true. A `+` on a non-empty list copies the last element, as it does for every field.
- **The edit-mode preview lifecycle lives in `Editor/Inspectors/UIAnimationPreview.cs`, not in an inspector.** Two inspectors drive it — a player's, and an asset's by way of a player — and a second copy is exactly the kind of thing that ends up with only two of the three load-bearing safety mechanisms. The button rows (`DrawRow` / `DrawFooter`) live there too, for the same reason.
- **Within one player the preview chains; it does not restore between Plays.** `CloseCredits` after `OpenCredits` has to start from the open state or it cannot be judged at all — restoring first made it start from rest, where a close with delayed From steps visibly misbehaves. **A different animation pressed while one is still running finishes the running one first** (`Complete(true)`, which works out of play mode and fires the SetActive callbacks on the way; an endless loop is left where it stands), so where the second starts never depends on when it was clicked — stopping it where it stood was reported as a bug. In play mode that now depends on the animation doing the interrupting: `COMPLETE` beside Interrupt Others matches the preview, `STOP` (what everything authored before it reads) stops the running one where it stands; the README says so. The preview never reaches the player's interrupt code at all — it calls `StopAll()` before `Play`. **`Reset` re-captures the start snapshot after applying the From values** (`EditorMarkPreviewStart`), so `Play` straight after `Reset` runs from the frame `Reset` showed — without it, Play restored the pre-Reset state (rest) and a close with delayed From steps played from the wrong place. **And every preview `Play` does the same thing first** — `ApplyFromState` then `EditorMarkPreviewStart` — so Play always equals Reset-then-Play. That is deliberately *not* play mode: an animation with `ApplyFromValuesImmediately` off holds each delayed From step at its current value until the step starts, and `CloseCredits` (which has it off) played from rest in the preview showed its buttons at rest, its text with no background, then everything snapping — reported as a bug, since in the game it only ever plays after `OpenCredits`. Proven on the UI prefab: Play from rest and Reset-then-Play give identical samples on all 30 animations. Two things keep chaining safe. (1) *Baselines are still captured at rest before every Play*: `EditorContinuePreview` notes the current state (a per-step **snapshot**, captured and restored through `CaptureBaseline` / `RestoreBaseline` themselves by swapping the snapshot into the baseline fields, so no step type can be covered by one and missed by the other), restores rest, re-initialises there — which also picks up Inspector edits — and puts the noted state back. The notes live on the *previous* runtime list's steps, which still point at what they resolved against. (2) *Play on the same animation again restores that play's start snapshot first*, so iterating on one animation still replays it from the top. A snapshot is only written back if the step still resolves to the same object, so retargeting mid-preview never writes one object's value onto another.
- **`RestoreBaseline` switches on the Type the baseline was captured under (`baselineType`), not the current `Type`.** Changing a step's Type mid-preview otherwise wrote a captured scale into a position. `RestoreBaseline` is editor-only in practice; nothing at runtime calls it.
- **Punch and shake capture a baseline even though nothing at runtime reads it.** It is what lets the preview put back a punch stopped half way through an oscillation — "it returns to its own start value" is only true when it runs to the end. Every impulse type is in `CaptureBaseline` / `RestoreBaseline` under the property it drives (position, `localEulerAngles`, `localScale`).
- **`ShakeRotation` and `ShakeScale` take a per-axis strength (`ToVector`); `ShakeAnchoredPosition` takes one number (`ToFloat`).** Not an inconsistency to tidy: DOTween's single-number rotation shake turns all three axes, and on a flat UI element X/Y rotation reads as it tipping over in 3D, so Z-only has to be expressible. `ShakeAnchoredPosition` predates this and its stored field cannot move.
- **Snapping is resolved as `step.Snapping || (animation.Snapping && !animation.SnapPerStep)`** — `UIAnimation.SnapsEveryStep` is passed into `BuildTween` as `snapAll`. The animation-wide box *adds to* a step's own box rather than replacing it, which is what makes this back-compatible with no migration: older data has the new fields false and snaps exactly the steps it always did. For the same reason the drawer shows a step's own box whenever it is ticked, even with Snap Per Step off — a setting that changes playback must never be invisible. Do not "simplify" this into Snap Per Step choosing between the two; that needs a migration flag and would silently change old data in builds, where `OnValidate` never runs.
- **The Type and Ease dropdowns are `GenericMenu`s drawn by the step drawer, not Unity's enum popup.** Type is grouped into sections derived from `IsImpulse` / `TargetKindOf` and sorted alphabetically *in the drawer*, so the enum's numbers — the serialized contract — never move to make the menu read well. `Custom Curve` is the first Ease entry, but the data is unchanged: it sets the same `UseCustomCurve` bool the old checkbox did, and the Ease row binds `BeginProperty` to whichever of the two fields it is showing so prefab-override bold and Revert follow what is visible. Menu callbacks write through `.Copy()`'d properties and `ApplyModifiedProperties`, because they run after the repaint that drew them.
- **The drawer reads enums with `intValue`, not `enumValueIndex`.** The index is a position in the declaration, only the number is the contract; they agree today only because every enum here is declared in value order.
- **The mode dropdown's tooltip comes from an empty `GUI.Label` drawn over the popup.** A popup does not show its label's tooltip, and the tooltip used to sit on the row's `To` label, where it read as explaining the row rather than the options. A label takes no clicks, so the popup under it still opens. The text is built per dropdown (`ModeTooltip`) from the options that dropdown actually offers — one shared tooltip described `Current` on a dropdown that did not offer it, and was reported.
- **The From dropdown does not offer `Current`, but still shows it when the data has it.** `FromMode = Current` never meant an offset: `HasAuthoredStart` excludes it, so the step ignores its From value and starts wherever it is — the same as the button reading TO. It is kept visible and never rewritten (all 14 `FromMode: 2` in the jam project have `UseFrom: 0`, so nothing authored relies on it), because changing what stored data means is the back-compat line. Contrast the To row with From on, which has always rewritten a stored `Current` to `Baseline` on draw — left alone, flagged here.
- **Save as Animation Set (`Editor/Menus/UIAnimationSetExport.cs`, on a player's Animations list) turns each filled target slot into a Target Path instead of emptying it.** An empty slot means the player's own object, so emptying one would make the set animate the wrong thing. It does not fail with a warning. The path goes up with `..` to the nearest shared ancestor and then down by name. It is kept only if `UIAnimationTargets.Resolve` with no slot gives back the exact object the slot held. Otherwise the target is under another root, or shares a name with a sibling, or is a second component of its type on one object. Then the path is written from the scene root, which misses and warns at play, and the Console lists it. On Complete listeners on a GameObject or Component are removed (`UnityEventTools.RemovePersistentListener`); the rest stay. The player is not modified. - **Nothing in the Inspector may read `UIMaterialInstance.Material`.** Its first read creates a material instance and assigns it to the Graphic — a side effect in the scene. The type check and Use Current read the source material through `UIAnimationTargets.SourceMaterialOf` (TMP's `fontSharedMaterial`, else `graphic.material`). The edit-mode preview itself still goes through `.Material` on material steps; that predates this and is untouched.
- **Editor-side target resolution lives in `Editor/UIAnimationTargets.cs`, and it mirrors `Resolve` without its side effects** (no warnings, nothing written to the step). A shared asset's steps resolve against the asset inspector's Preview On player, registered in a static map in `UIAnimationAssetEditor` (`PreviewPlayerFor`) because the drawer only knows the serialized object it draws.
- **`UIAnimationSimulation` plays position, size, scale and rotation steps forward on paper**, for the gizmos, the path editor's start point and Use Current's `Current` offset. It must follow playback, and does so by *sharing* code rather than copying it wherever it can: steps are laid out by `UIAnimationPlayer.LayOutSteps` (extracted from `BuildSequence` for this — play-path fingerprint byte-identical), stepped eases go through a real `UIAnimationSteppedEase`, and paths through `UIAnimationPathEditor.Evaluate`. The rules it copies: From state applied first in step order (the preview's rule); steps act in `(start time, index)` order so a later-starting step overrides and among equal starts the lower row wins; a step's start is read at its start time; paths are followed at constant speed (DOTween's `ConvertToConstantPathPerc`); snapping rounds. Checked against the real preview at every drawn moment: 485 moments across the UI prefab and both tester scenes, all within 0.07 units — the residue is DOTween's own path length table. It works from **rest**, which during a preview is what `UIAnimationPreview` captured before anything moved (`NoteRest` / `ForgetRest`), so drawings stay put while the preview moves the objects.
- **Gizmos draw from `UIAnimationPlayerEditor.OnSceneGUI`, which Unity only calls for editors the Inspector has built.** "Expanded" in the gizmo modes is `isExpanded` on *that editor's* `serializedObject`. **But `OnSceneGUI` must not touch `serializedObject` or `targets`**: Unity logs an error with a stack trace on every call, which is every Scene view repaint — it flooded the Console and made the Editor feel sluggish. The editor keeps a reference (`sceneSerialized`) taken in `OnEnable` and refreshed in `OnInspectorGUI`, null when multi-editing. Rainbow colours apply in `Expanded Steps` only (`EffectiveColors`); everywhere else it is Distinct, with the stored choice kept. The simulation behind the gizmos costs about 1.3 ms for all 30 animations in the UI prefab. Two consequences found the hard way: a harness that changes the selection while the Editor is in the background must `ActiveEditorTracker.sharedTracker.ForceRebuild()` or nothing draws, and `isExpanded` set through a *different* `SerializedObject` does not reach an editor that already exists.
- **Use Current's `Baseline` and `Current` only work inside a preview, on purpose.** Out of a preview the object's current value *is* its rest, so both would always store 0. Inside one, rest is the preview's capture and Stop and Restore puts the posed object back — the Animation window's record workflow. **That workflow needs the preview to survive selecting the object being posed**, and it did not at first: the player inspector's `OnDisable` ended the preview on any selection change, so selecting the ball to drag it restored it, and back on the player Baseline and Current were greyed out — reported as "clicking record does nothing", and missed by a scripted test that never changed the selection. `EndIfOwnedBy` now leaves the preview running, owned by nobody, while the selection is on the player, its shared asset or any object it animates, and `Selection.selectionChanged` ends an unowned one once the selection leaves. An owner that still exists (a locked inspector, or a plain `object` from a harness) is left to end its own preview. The asset inspector remembers its Preview On per asset in the static map for the same reason. Rotation reads are wrapped to the nearest angle to zero (`Mathf.DeltaAngle`): a Rotation step is `FastBeyond360`, so a copied `350` would spin the long way.
- **The preview unwinds itself from `[InitializeOnLoad]` hooks** — `playModeStateChanged` at `ExitingEditMode` (which runs *before* Unity backs the scene up for play mode, so the restore is what play mode starts from and returns to) and `beforeAssemblyReload` — not only from an inspector's `OnDisable`. The inspector hook (`OnDisable`) and `Selection.selectionChanged` cover selection change — see Use Current for why it waits for the selection to leave.
- **`EditorSuppressSound` is on for the whole preview, not just while the sequence is built.** Sounds fire from sequence *callbacks* during playback; scoping it to construction silenced nothing, and every preview of a sound step called `UIAnimationAudio.Shared` in edit mode — where `DontDestroyOnLoad` **throws after the GameObject already exists and before the static is assigned**, leaking one `UI Animation Audio` into the open scene per call, outside the Undo record. `Shared` now returns null out of play mode as a second guard.
- **A filled target slot skips the Target Path entirely — the path is not even looked up.** It used to be resolved anyway, and a path that missed set `targetPathMissed`, which then made `HasTarget` skip a step that had a perfectly good direct reference. The drawer greys the path out while the slot is filled so the precedence is visible.
- **An asset inspector's "Preview On" player is not a serialized field on the asset.** A scene reference is the one thing an asset cannot keep, which is the problem the slot exists to work around. It lives in the editor, remembered per asset in a static map until the next domain reload, so a new inspector on the same asset finds it set.
- **Movement paths (`UseCustomPath` / `PathShape` / `Waypoints`) are built on DOTween's generic `PathPlugin`, not a shortcut** — `DOTween.To(PathPlugin.Get(), getter, setter, new Path(...), duration)`, the same call DOTween's Rigidbody module makes. That is what lets one path drive `anchoredPosition`, `sizeDelta` or `localScale`. Three plugin behaviours it works around, measured on DOTween 1.3.030: it **throws a NullReferenceException at startup without `SetTarget(transform)`**; it **ignores `From()`**, so an authored From is supplied by making the getter return it; and it **prepends the start as a point unless the first waypoint already equals it**. `Rotation` is excluded on purpose (quaternion, not Euler), and an empty point list falls back to the ordinary tween so it behaves exactly like the box unticked.
- **Waypoints follow `To`'s mode rather than having their own.** `SetRelative` offsets every path point by the start, To included, so a separate mode would be a second answer to a question To already answers. The cost is in mirroring: when the mirror changes To's mode (From/To in different modes, or no-From with an Absolute To), the points can't be converted without the runtime baseline, so `UIAnimationMirror.PathSpaceChanges` reports them instead of guessing.
- **`UIAnimationPathEditor.Evaluate` reimplements DOTween's Catmull-Rom because the real `Path.GetPoint` is `internal`, and its end conventions are deliberately not the textbook ones:** the control point before the first point is the *second* point, and the one after the last is the last point mirrored through the one before it. Checked by sampling a real path tween — every position lies within 0.001 units of the drawn curve. "Fixing" it to reflected ends draws a curve the object does not follow. The same asymmetry is why a mirrored *Curved* path retraces its original only to within about 1.5 units on a 200-unit path, while *Linear* is exact.
- **The path is created with a transparent gizmo colour.** DOTween draws running path tweens in the Scene view at the raw point values, which for `anchoredPosition` are not world positions.
- **The Scene-view path editor follows Unity's Edit Collider pattern:** it hides `Tools` (restoring the previous value, and again from `beforeAssemblyReload`, because `Tools.hidden` survives a domain reload), registers a passive default control so clicks on empty space cannot deselect the player, and writes only through a `SerializedObject` for Undo and prefab overrides. It only edits `AnchoredPosition` / `LocalPosition` on a player outside play mode. It draws from the rest state and the step's simulated start (`UIAnimationSimulation`), so a path in a later step starts where the earlier steps leave the object, and it keeps drawing through a preview — it used to draw from where the object sat, and paused while previewing, which read as the path vanishing on Play. The gizmos skip the step it is editing.

- **A Custom Property step stores its member as three plain values — the component's `Type.FullName`, the member's name and a `UIAnimationPropertyKind` — and resolves them once, in `Resolve`.** The component is found by matching `GetType().FullName` against what is actually on the object, not with `Type.GetType`, so a script moving assembly does not break a step. The kind is stored rather than re-derived because a shared asset with no Preview On has nothing to derive it from, and the drawer still has to draw the right From / To fields. A member whose type no longer matches the stored kind is a warning and a skipped step, never a guess. All the lookup rules live in `UIAnimationProperty.cs` (`UIAnimationProperties.TryLocate` / `FindMember` / `CollectMembers`), shared by playback, the Property dropdown and the type check, so the dropdown can never offer something playback then rejects.
- **`FindMember` walks up the type hierarchy one `DeclaredOnly` declaration at a time.** A flat `GetProperty` reports a name re-declared with `new` as ambiguous, and an override that only replaces the getter is a declaration with no setter. The walk skips it and binds to the base declaration, and a delegate made from the base accessor still dispatches to the override (checked). The walk stops at `UnityEngine.Object` / `Component` / `Behaviour` / `MonoBehaviour`, which is also what keeps `name`, `tag` and `enabled` out of every component's list.
- **Property accessors are bound with `Delegate.CreateDelegate`, the call UnityEvent makes for a persistent listener,** so a tween has no reflection or boxing per frame. Public fields go through `FieldInfo` and box; they are the rarer case. IL2CPP with Managed Stripping above Minimal can strip a setter only this tool calls. That is documented in the README (`link.xml`), not worked around.
- **Nothing in the Inspector calls a Custom Property's getter except the Use Current Value button's click.** A getter is arbitrary code, and the type check, the dropdown and Use Current's enabled state all run every repaint, so they only look members up. The same thinking as *Nothing in the Inspector may read `UIMaterialInstance.Material`*.
- **`CapturePropertyBaseline` and `RestorePropertyBaseline` catch exceptions; no other step type does.** Their getters and setters are someone else's code. `Initialize` captures every step of every animation in one pass, and the preview's End restores every step in one pass. One throwing member must not leave the player half-initialised, or the scene half-restored. The member that threw is warned about once and its step skipped.
- **`baselineMember` / `snapshotMember` exist for the same reason `baselineType` does:** `RestoreBaseline` writes back through the member the value was *read* from, so picking a different member mid-preview never writes one member's value into another. `SwapSnapshot` swaps them with the rest of the snapshot fields.
- **A counted-number text (`NumberText`) keeps two baselines:** the parsed number (`baselineFloat`, what `Baseline` endpoints measure from) and the original string (`baselineText`, what is restored). Restoring the number re-formatted would turn `Score: 120` into `0`. `ParseNumber` only reads a text that is just a number, in the current culture and then the invariant one, and reads anything else as 0 — deliberately not clever about prefixes. `FormatNumber` falls back to the plain number on a `FormatException`, since that would otherwise throw every frame.
- **Typewriter text offers `Absolute` and `Baseline`, never `Current`.** DOTween's string plugin does support relative (it appends), but a mirrored copy cannot take appended characters back off. `Baseline` on text is "resting text + typed text", which mirrors exactly. The drawer's `offersCurrent` and the mode tooltip say so. Text uses `SetOptions(richText: true)`, as `DOText` does, so a tag is never shown half-written (checked).
- **An `int` member's From / To live in the float fields and are drawn with an `IntField`.** There are no `FromInt` / `ToInt` fields; `ValueKindOf(UIAnimationPropertyKind)` returns `Int` only so the drawer knows to draw whole numbers. `FromText` / `ToText` are the only value fields the step type added.
- **The edit-mode preview runs the member's real setter,** so whatever that setter does happens outside play mode (`Slider.value` invokes `onValueChanged`, whose default *Runtime Only* listeners stay silent in edit mode). That is inherent in previewing an arbitrary property, and the README says so rather than the preview trying to guess which setters are safe.

DOTween behaviours worth knowing, all silent when violated: `SetLink` is a no-op on a tween inside a Sequence (apply it to the outer `Sequence`); a tween must be configured fully *before* `Append`/`Join`, since `DoInsert` sets `creationLocked` and `From`/`SetEase`/`SetRelative` then do nothing; `.From(value)` defaults to `setImmediately: true` and writes during construction rather than at t=0; a stencil `Mask` defeats material instancing because `StencilMaterial.Add` caches a copy that never re-syncs (`RectMask2D` is fine, and `MaterialPropertyBlock` does not work with UGUI at all); `TextMeshProUGUI` ignores `Graphic.material`, so use `TMP_Text.fontMaterial` and never destroy it. `SetUpdate(true)` is required for UI that animates while `Time.timeScale == 0`.

**DOTween's kill semantics differ between play mode and edit mode, and this will make an edit-mode test lie.** Measured against DOTween 1.3.030 in Unity 6000.3:

| | `tween.Kill()` | `DOTween.Kill(id)` / `KillAll()` / `Clear()` | `Pause()` | `Complete()` |
| --- | --- | --- | --- | --- |
| Play mode | despawns immediately, `OnKill` fires | same — immediate, `OnKill` fires | works | `OnComplete` then `OnKill`, both immediately |
| Edit mode | **nothing** — `IsActive()` stays true, `OnKill` never fires | **work** — the tween goes inactive | works | works, both fire |

The cause: **DOTween never initialises out of play mode** (`DOTween.initialized` stays false; its init check bails on `!Application.isPlaying`), and `Tween.Kill()` returns early when it is not initialised. The filtered operations behind `DOTween.Kill(id)` / `KillAll` have no such check. **A test that kills a tween out of play mode and asserts on the result is measuring the Editor, not the game.** This cost a wrong conclusion once: `OnKill` was written off as never firing for a plain `Kill()`, and a polling `Update` was added to work around a problem that does not exist in a build. Check tween lifetimes in play mode.

It also cost a real bug in the edit-mode preview, because **`DOTweenEditorPreview.Stop()` does not kill either** — it only stops calling `DOTween.ManualUpdate`. A stopped preview's sequence stayed active and *playing*, so the next preview's update loop resumed it alongside the new one, replaying its callbacks: "Stop and Restore" appeared to work (values restored) and the next Play then continued every old preview from where it left off. That is why `UIAnimationPreview` tags every sequence with an id, pauses it and kills it with `DOTween.Kill(id)`.

Separately: **`DOTween.Kill(x)` matches by a tween's *target or id*, so `DOTween.Kill(sequence)` matches nothing and is a silent no-op** — it is not the same call as `sequence.Kill()`, despite reading like it.

## FlipbookAnimation

No dependencies — not even DOTween. It only writes `Image.sprite`, so DOTween can move, scale and fade the same object at the same time; that split is intentional.

`UISpriteFlipbook` cycles an `Image` through a list of sprites. `UIFlipbookSelectable` sits *beside* a `Selectable` and picks the clip for its interaction state (Disabled > Pressed > Selected > Highlighted > Normal, matching Unity's own priority), leaving `onClick`, navigation and transitions untouched. `UIFlipbookClipAsset` is an optional ScriptableObject for sharing one clip across many objects.

Per clip: frames, FPS, loop mode (`Once` / `Loop` / `PingPong`) and timing mode (`Constant FPS` / `Random Offset` / `Per Frame Durations`).

Things that look wrong but are intentional:

- **A clip that merely ran out is not the same as one that was `Stop()`ped, and `OnEnable` tells them apart via `stoppedExplicitly`.** `Stop()` sets it, completion does not, `Play()` clears it. Without this a `Once` clip plays exactly once per scene load, and a panel shown, hidden and shown again sits frozen on its last drawing.
- **Randomised frame timing is rolled per pass on the *player*, never on the clip.** One clip asset can drive hundreds of objects, and rolling on the clip would give them all identical timing — the exact thing randomising was meant to prevent. `RandomStartFrame` lives on the player for the same reason.
- **Ping-pong turns at `count - 2`**, not `count - 1`, so the end drawings are not held for a double beat. A 4-frame clip reads `ABCDCBABCDCB`.
- **`Selected` deliberately does not fall back to `Highlighted`.** A button keeps EventSystem selection after a click, so borrowing the hover look while the mouse is elsewhere reads as a stuck button. An empty `Selected` means "no focus look".
- **Do not set the Selectable's Transition to `Sprite Swap`** — it writes `Image.sprite` itself and fights the flipbook. `OnValidate` warns about it.
- **`LoopMode` replaced a serialized `bool Loop`, and Unity cannot convert between them.** `MigrateLoop()` reads the legacy bool once, using the older `defaultsFilled` flag to tell authored data from a zero-filled new element. Both hidden fields must stay for any project still holding pre-migration assets.
- Sprite thumbnails use `GUI.DrawTextureWithTexCoords` over `sprite.textureRect` rather than `AssetPreview`, which loads asynchronously and returns null on the first repaints.
- The frame sort is numeric-aware, so `frame_2` precedes `frame_10` and `frame_007` lands beside `frame_7`.

## SelectableEvents

The project author's own code. `SelectableEvents` exposes UnityEvents for hover, unhover, press, release, click, select, deselect and submit on anything deriving from `Selectable`.

It implements the same EventSystem handler interfaces as `UIFlipbookSelectable`, and **that is fine** — the EventSystem delivers each event to *every* handler on the object, so both receive it and the Selectable's own behaviour is unaffected. ## Shared conventions in the Claude-authored tools

Both use the same patterns, and anything added to them should too.

**Inspector-authored data classes need a `FillUnsetDefaults()` called from the owner's `OnValidate`.** Unity does not run C# field initialisers for elements added with `+` on a serialized `List<T>` — a new element is zero-filled, so `= 12f` / `= true` silently do not apply. `FillUnsetDefaults` only writes fields still at their zero value, so authored data is never clobbered. Where `false` is both "never set" and "the user unticked it", a hidden `defaultsFilled` bool is what distinguishes them.

**Serialized enums are stored as integers, and those integers are the contract.** Every enum here assigns its values explicitly (`Scale = 12`) so reordering the lines is harmless. *Changing* a number, or reusing a retired one, repoints every asset authored against it with no error and no warning. This cost a day once: alphabetising `UIAnimationStepType` turned 16 authored `Scale` steps into `GraphicAlpha` steps and faded a menu to invisible. It reads like lost references or a corrupt prefab, so **if animations "disappear", check the enum's history before blaming the asset** — the fix is to remap the stored integers, never to reorder the enum back. Any new Inspector-authored enum should assign its numbers explicitly from the start.

**Edit-mode preview animates real scene objects, and three things make that safe.** Both tools have one; all three mechanisms are load-bearing. Capture before and restore after, *per property* — never a blanket `EditorJsonUtility` round-trip of the component, which also rewrites object references and blanks things like an `Image`'s sprite. Re-capture baselines before *every* preview, so relative endpoints do not drift on repeats. Clear callbacks, because an `On Complete` UnityEvent is wired to arbitrary game code that must not run outside play mode. Plus: only one preview at a time (that is what guarantees the captured state belongs to the object being restored — the DOTween preview chains animations *within* one player, see its entry), one `Undo` entry as a backstop, `EditorUtility.SetDirty` on each touched object, and an unwind on selection change (the DOTween preview waits until the selection leaves the player and everything it animates — see Use Current), play-mode change and assembly reload — registered from an `[InitializeOnLoad]` static constructor, not left to an inspector's `OnDisable`. And make sure a stopped preview is actually *dead*: out of play mode the ordinary DOTween kill does nothing (see the DOTween table).

**Right-click menus are scoped by target object, not by type name.** `SerializedProperty.type` and `propertyPath` report *unqualified* names, so a namespace does not disambiguate them and another project's `UIAnimation` or `Frames` list would match a string comparison — require your own component as `serializedObject.targetObject` instead. Also `.Copy()` the property handed to the callback, since menu items run after it goes out of scope, and register `contextualPropertyMenu` **once per folder**: every handler appends to the same menu. **Start a handler's entries with `Separate(menu)`, never a bare `AddSeparator`.** Unity 6000.3 ends its own part of every property menu with a divider before any handler runs, so an unconditional one drew two in a row on Windows (reported with a screenshot; the author had not seen it on macOS). `GenericMenu` has no public item list, so `Separate` reads the private `m_MenuItems` and adds the divider anyway if it can't. To see what a menu really contains, call the internal `EditorGUI.FillPropertyContextMenu(property, null, null)` by reflection and read `m_MenuItems` (each `MenuItem` has public `content` and `separator` fields). It throws outside `OnGUI`, so run it from a utility window's `OnGUI` via `RepaintImmediately` (see the drawer-exception trick under Verifying).

**When copying Inspector data, use `JsonUtility`, not `EditorJsonUtility`.** Despite the names, the plain one preserves `UnityEngine.Object` references (`{"instanceID":-228892}`) and the Editor one destroys them (`{"instanceID":0}`), because it serializes the way an asset file does, where a reference is a file ID an in-memory scene object does not have. This was backwards once and dropped every target slot on paste.

**Two Unity API limits these tools work around.** `[Range]` clamps typed input as well as the slider, so it cannot express "the slider stops at 12 but you may type 24" — draw the slider and the field separately, and only adopt the slider when it actually moved. And `GetPropertyHeight` is not given the width it will be drawn at, so a drawer whose height depends on wrapping has to find it another way. The step drawer's warning row does it with `EditorGUIUtility.currentViewWidth`, which *is* live there: everything between the view's edge and the drawer (Inspector margins, list handles and padding) is a fixed number of points, so `OnGUI` records `currentViewWidth - position.width` per property path (skipping `Layout` events, whose rect is a dummy) and the measuring pass lays out at `currentViewWidth` minus that. It matches the draw to the point and follows a window resize with no lag — checked by screenshot at 320 / 420 / 760 px, three / two / one lines. A new view's first measure uses a guessed margin; `ReorderableList` re-measures on its first repaint anyway (a changed list rect invalidates its height cache), and `OnGUI` calls `HandleUtility.Repaint()` whenever the recorded margin changes. Anything that does not wrap should still use a fixed number of rows and truncate, like the step header.

**Testing enable-time logic requires reflection.** Edit mode does not deliver `Awake` / `OnEnable` / `OnDisable` to a component without `[ExecuteAlways]`, so a test that toggles `SetActive` exercises nothing and quietly passes. Invoke the callback directly instead. The mirror-image trap: in *play* mode `AddComponent` runs `Awake` immediately, so a test that fills in serialized fields afterwards is talking to a component that has already initialised against empty ones. Reset the lazy-init flag as well as setting the field.

## Verifying a change

**This repo is loose drop-in folders, not a Unity project** — no `Assets/`, no `ProjectSettings/`, no Editor to compile against. Nothing here can be claimed to compile without actually compiling it somewhere else — a real project (below), or the offline setup further down, which gets as far as compiling against real assemblies and running pure logic.

**For `DOTweenAnimationPlayer`, `GameCraftSep2026Jam` links this repo directly.** Its `Packages/manifest.json` has `"com.rmfandyplayz.dotween-ui-animation": "file:../../UnityAnimationTools/DOTweenAnimationPlayer"` (on the jam's `package-migration` branch until the author merges it). Every edit here therefore compiles there on the next refresh (`AssetDatabase.Refresh()` from `eval`), with no copying. Because a `file:` package is writable, **Unity writes `.meta` files into this repo**, so check `git status` here after any session that added a file, and commit those metas. `GameCraftSep2026P2Jam` installs the package by git URL, like any other project.

For the other two tools, the old recipe still works: copy the tool folder into a real Unity project that has DOTween Pro, under a temp path like `Assets/_CompileCheck/`, **without the `.meta` files**, so it can't collide with an existing copy's GUIDs. Compile, then delete the folder and recompile so no stale assemblies are left. The jam holds older *un-namespaced* copies of them, so a staged copy sits beside those without conflict. Ask before using a different project.

**The strongest available regression test is a fingerprint diff against a real project's authored animations, and it is cheap.** Since the jam links this repo (above), "before" and "after" are two states of *this* repo's working tree: stash here (`git stash push -u -- DOTweenAnimationPlayer`, the `-u` matters, see below), refresh the jam, fingerprint, `git stash pop`, refresh, fingerprint. (Until September 2026 the jam held a hand-upgraded copy under `Assets/Scripts/UI/Utility/DOTweenAnimationPlayer/`, which its `UIAnimatorTest` branch still has.) The package move itself was proven this way, old in-Assets copy against package: 71 animations, 426 samples, byte-identical, deterministic across two runs each. The harness was `Assets/_Check/Editor/PackageFingerprint.cs`, deleted afterwards; it is the play-path fingerprint described below. The older play-mode version: in play mode, walk every `UIAnimationPlayer` in the scene, `Play` each animation, `Goto` five points across its duration, and write out every scene property that moved away from rest. Do that before and after and diff the text. Two things that make the fingerprint trustworthy: **build a fresh sequence per sample point** (rewinding one sequence accumulates on any relative or `To: Current` step, which is a property of `Goto`, not of the animation), and **run it twice before trusting it** to prove it is deterministic. Enumerate names through `EditorCollectAnimationNames`, not `EditorAnimations`, or a player that moved to a shared asset reads as empty.

**When a change only touches target resolution or baselines, a cheaper edit-mode diff is enough and needs no play mode.** Call `EditorPrepareForPreview()` on every player in the scene and dump, per runtime step, the private resolved-target fields, `targetPathMissed` and the baseline fields by reflection, plus any warnings logged. Take it on the new code, then `git stash push -u -- DOTweenAnimationPlayer` in this repo (the `-u` matters: an untracked new file that uses new APIs would otherwise break the old code's compile), recompile, dump, `git stash pop`, recompile, and diff. Keep the dump harness compatible with both versions — reflection only.

**The cleanest play-path fingerprint needs no play mode and never touches the user's scene.** Instantiate `Assets/Prefabs/UI/UI.prefab` into an additive scratch scene (`NewScene(..., Additive)`), and for every player and animation, six times per animation: `EditorPrepareForPreview()`, `Random.InitState`, `player.Play(name)`, `DOTweenEditorPreview.PrepareTweenForPreview(seq, true, true, false)`, one `DOTween.ManualUpdate(t, t)` to the sample point, dump the targets, then `DOTween.Kill(id)` / `StopAll()` / `EditorRestoreBaselines()`. It calls `Play` directly, so it measures `BuildSequence` / `BuildTween` and nothing the preview adds, and it uses only APIs every version has. It is how the `LayOutSteps` extraction was proven byte-identical (30 animations, 180 samples, deterministic across two runs).

It has since been extended to the tester scenes: 71 animations, 426 samples. They are copied to `Assets/_Check/` with `AssetDatabase.CopyAsset` and opened additively, so the fingerprint never touches the tester scene the Editor has open (usually `UITester.unity`). A cheap dump that catches Custom Property members too:

- `EditorJsonUtility.ToJson` of every component, plus `activeSelf`.
- Material float and colour properties for anything with `UIMaterialInstance`.
- Only what differs from rest is written.

TextMeshPro's JSON changes after any animation (internal bookkeeping) and never goes back. That shows up as "not restored" lines, the same in every run, and is not a bug.

**A cheap behavioural fingerprint also runs in edit mode, through the preview.** Since preview `Play` applies the From state first, this one now differs from play mode for animations with `ApplyFromValuesImmediately` off — use the direct play-path fingerprint above for anything about runtime behaviour. For every player and animation in the scene: `UIAnimationPreview.End()`, seed `Random.InitState` (shake is random), `UIAnimationPreview.Play`, read the sequence out of the private static `running` by reflection, then `DOTween.ManualUpdate` through five equal slices of its duration, dumping every target's properties after each. Old vs new via the same stash procedure; it needs only APIs both versions have. It exercises `BuildSequence` / `BuildTween` exactly as play mode would, and it is how the Snapping and punch/shake change was proven byte-identical on the 33 animations in `UI.unity`. It does not cover anything play-mode-only (lifetimes, `OnKill`).

**Edit-mode preview can be tested without waiting on editor frames.** Every preview sequence is `UpdateType.Manual`, so a harness can call `UIAnimationPreview.Play` and then drive time itself with `DOTween.ManualUpdate(dt, dt)` in a loop, all inside one `eval`, in an additive scratch scene. That is exact and repeatable where sleeping between `eval` calls is not — the round trip is long enough to swallow a whole 0.6s animation. For things only the real editor does (entering play mode), start the preview in one `eval` and use `editor_play` / `editor_stop`; a plain `object` as the requester keeps any inspector's `OnDisable` out of the result.

**Compile check on the author's Windows machine with the Editor closed — about a minute, touches nothing in the jam.** Unity leaves its own compiler response files in `GameCraftSep2026Jam/Library/Bee/artifacts/2000b0aE.dag/` (`2000b0aP.dag/` is the player build, without `UNITY_EDITOR`).
